Spring Boot + Netty App 端技术方案 (deepblue.inaction_02_springboot)

一、目标
	- 自己做一个 App 端, 本地启动的 Spring Boot + Netty 服务当作服务器。
	- 第一步: App ⇄ 服务器 通信 (登录、心跳、服务端推送)。
	- 第二步: AppA ⇄ AppB 通过服务器互发消息。
	- 约束: 只研究 Netty, 不引入 WebSocket; App 直接用 Netty TCP 客户端连现有的 9000 端口。


二、方案选择
	- 为什么不用 WebSocket / H5 网页:
	    · 浏览器不能发起原始 TCP 连接, 网页 App 必须走 WebSocket;
	    · WebSocket 不在本次研究范围内, 所以放弃网页 App, 改用原生程序 + Netty TCP 客户端。
	- 两条可选路线:
	                    A. 桌面 App (Swing 窗口)                       B. Android 手机 App
	    Netty 部分      完全复用 NettyClientInitializer / 编解码器 /    基本照搬, 依赖改用 netty-handler + netty-codec
	                    ClientHandler                                  (netty-all 对手机太大)
	    放在哪          本工程内新建一个包                              新建 Gradle Android 工程
	    要装什么        不用装                                          Android Studio + SDK (数 GB), 需学 Android 基础
	    AppA ⇄ AppB     开两个窗口, 或同网络的另一台电脑                两台手机, 或手机 + 模拟器
	    网络            本机 localhost, 没问题                          手机要能访问电脑 9000 端口 (见 六、风险)
	- 结论: 先做 A。
	    · 研究重点是 Netty, A 能把精力放在 Netty 客户端上, 不用分心学 Android;
	    · A 中的 Netty 代码将来搬到 Android 几乎不用改, 只需替换界面层。
	- 当前环境: 本机未安装 Android Studio / Android SDK (2026-10-27 检查)。


三、现状: 已有能力 (直接复用, 服务端不用改)
	- 登录 / 绑定用户: LOGIN / LOGIN_OK, 会话表 ChannelSessionManager。
	- App ⇄ 服务器: 心跳 PING / PONG, 读空闲踢人, 服务端主动推送 PUSH。
	- AppA ⇄ AppB: CHAT 经会话表找到对方 Channel 转发; 对方不在线回 ERROR。
	- 重复登录踢下线 KICKED, 客户端断线指数退避重连。
	- 协议: 一行一个 JSON, 例如 {"content":"hi","to":"jerry","type":"CHAT"}, from 由客户端自动填。
	- 客户端现成代码: MineNettyClient、NettyClientInitializer、ClientHandler、JsonMessageDecoder / JsonMessageEncoder。
	- 测试、日志 (类名 方法名 invoke, userId=...)、启动脚本 scripts\netty-server.cmd / netty-client.cmd。


四、需要新增 / 修改的内容 (路线 A)

	1. 服务端 (可选, 纯 Netty 内容): 在线用户实时广播
	    · 现状: App 想知道谁在线, 只能调 HTTP 接口 GET /netty/online。
	    · 新增消息类型 (MessageEnum):
	        ONLINE_LIST    服务端 → 客户端  登录成功后下发当前在线用户列表
	        USER_ONLINE    服务端 → 客户端  有人上线时广播
	        USER_OFFLINE   服务端 → 客户端  有人下线时广播
	    · 修改 ChannelSessionManager.bind / unbind: 绑定、解绑成功后通过 TCP 广播给其他在线用户。
	    · 效果: App 的联系人列表实时刷新, 不依赖 HTTP。

	2. ClientHandler 把消息交给界面 (修改)
	    · 现状: ClientHandler 收到消息只打日志。
	    · 新增回调接口 (例如 ClientListener):
	        onConnected / onMessage(Message) / onDisconnected / onKicked / onReconnecting(delaySeconds)
	    · 终端客户端 MineNettyClient 和桌面 App 各自实现这个接口。

	3. 线程切换 (Netty 重点)
	    · 收消息: ClientHandler 运行在 Netty EventLoop 线程, 界面只能在界面线程更新;
	      Swing 用 SwingUtilities.invokeLater, Android 用 runOnUiThread, 道理相同。
	    · 发消息: 点 "发送" 时在界面线程调用 channel.writeAndFlush,
	      Netty 会自动把写操作封装成任务交回该 Channel 的 EventLoop 执行, 线程安全, 不用加锁。
	    · 注意: 界面线程里不要 sync() / await() 等待写完成, 用 addListener 处理结果。

	4. 桌面 App 窗口 (新增, 例如 client/MineNettyApp)
	    · 登录框: 输入 userId、服务器地址、端口 (默认 127.0.0.1:9000)。
	    · 在线用户列表: 点一下选中聊天对象 (依赖第 1 点; 不做第 1 点则只能手动输入对方 userId)。
	    · 聊天记录: 自己的消息在右、别人的在左, PUSH / ERROR / KICKED 居中显示。
	    · 输入框 + 发送按钮: 组装 CHAT 消息, 复用 MineNettyClient.parseInput 的校验规则。
	    · 状态栏: 连接中 / 已连接 / 重连中 (N 秒后重试) / 被踢下线。

	5. 测试与文档
	    · 集成测试: 两个 Netty 客户端经服务端互聊; 若做第 1 点, 验证上线 / 下线广播。
	    · 更新 springboot_netty_使用流程.txt 与 Netty_9_SpringBoot案例流程.html。

	6. 工作量估计
	    · 新增约 3 ~ 4 个类 (App 窗口、回调接口、可选的在线列表消息处理);
	    · 小改 ClientHandler、MineNettyClient、MessageEnum、ChannelSessionManager;
	    · 服务端主流程不改。


五、启动与验证方式 (完成后)
	1. 终端 S: scripts\netty-server.cmd
	2. 启动两个桌面 App 窗口, 分别以 tom、jerry 登录。
	3. 预期:
	    · 两边在线列表互相出现对方;
	    · tom 选中 jerry 发 "hi", jerry 窗口左侧出现消息; 反之亦然;
	    · 终端客户端 (scripts\netty-client.cmd spike) 与 App 也能互聊 (同一协议、同一会话表);
	    · 关闭服务端: App 状态栏显示重连倒计时; 服务端重启后自动重连并重新登录;
	    · 同一 userId 再开一个窗口: 旧窗口显示被踢下线, 不再重连。


六、风险: 手机 / 其他电脑连本机 (路线 B 或跨机器时才需要)
	- 本机情况 (2026-10-27 检查):
	    · 有线网络, IP 10.54.5.138, 网络类型为公司域网络 (DomainAuthenticated);
	    · 防火墙中没有 Java 的入站放行规则。
	- 可能的问题: 公司网络常见 WiFi 与有线隔离、终端之间禁止互访, 防火墙可能由组策略统一管理。
	- 先自测: 启动服务端后, 在另一台设备上执行 telnet 10.54.5.138 9000 (或用浏览器访问 http://10.54.5.138:8080/netty/online)。
	- 被拦时的办法:
	    · 放行端口 (需管理员权限, 公司电脑可能不允许):
	        netsh advfirewall firewall add rule name="netty-demo" dir=in action=allow protocol=TCP localport=8080,9000
	    · Android 真机: USB 连接后 adb reverse tcp:9000 tcp:9000, 手机直接连 localhost:9000, 不走 WiFi;
	    · 都不行时, 先在本机多开窗口验证, 网络打通后再换设备。


七、暂不做 (后续可选)
	- 身份认证: 现在随便填名字就能登录, 也能冒用别人的名字; 正式使用需密码或 token。
	- 离线消息 + ACK 重发: 对方不在线时消息目前会丢; 这是 IM 与 demo 差距最大的地方。
	- 聊天记录持久化、群聊、图片 / 文件、TLS 加密 (Netty SslHandler)、集群部署 (Redis 记录用户所在节点 + MQ 转发)。
	- WebSocket / H5 网页 App: 不在本次研究范围 (区别与共用见 八)。


八、Netty 与 WebSocket 的区别与共用

	1. 定位: 不是同一类东西, 不存在 "二选一"
	    · Netty 是 Java 网络编程框架 (一个库), WebSocket 是应用层协议 (RFC 6455)。
	    · 类比: Netty 是 "造车工具", WebSocket 是 "交通规则"; 好比 Spring 与 HTTP, 不能比谁好。
	    · Netty 可以实现 WebSocket, 也可以实现自定义 TCP 协议、HTTP、MQTT ...;
	      WebSocket 也可以不用 Netty 实现 (Tomcat、Spring WebSocket、Node.js、浏览器)。

	                    Netty                                           WebSocket
	    是什么          Java 网络编程框架                               应用层协议 (标准规范)
	    解决什么        怎么高效收发字节: 线程模型、Pipeline、          浏览器与服务器怎么建立双向长连接,
	                    ByteBuf、编解码、心跳                           消息按什么格式传
	    谁来用          Java 程序员写服务端 / 客户端                    浏览器、App、服务器之间约定的 "说话方式"

	2. 作为协议: 自定义 TCP 协议 (本案例) vs WebSocket
	                    自定义 TCP 协议 (一行一个 JSON)                 WebSocket
	    建立连接        TCP 连上即可发送                                先发 HTTP 请求 (Upgrade: websocket), 同意后升级
	    消息边界        自己定: 本案例用 \n, 常见还有长度字段           协议自带帧, 每帧有长度, 不用自己处理粘包 / 半包
	    心跳            自己定: PING / PONG 消息                        协议自带 ping / pong 控制帧
	    浏览器能否用    不能, 浏览器发不了原始 TCP 连接                 能, 这是它最大的价值
	    防火墙 / 代理   自定义端口, 公司网络、代理容易拦                走 80 / 443, 与普通网页一样 (wss)
	    开销            最小, 格式完全自控                              多一次握手; 每帧 2 ~ 14 字节头, 客户端数据需掩码
	    典型场景        RPC、游戏、物联网、内部服务、原生 App           网页聊天、网页实时推送、在线协作、行情页面

	3. 在 Netty 里, WebSocket 只是几个 Handler (属于 ④ 编解码 与 ⑥ 连接生命周期)
	    现在 (自定义行协议):
	        Head → idle → LineBasedFrameDecoder → StringDecoder → JsonMessageDecoder → ... → business
	    换成 WebSocket:
	        Head → idle → HttpServerCodec → HttpObjectAggregator → WebSocketServerProtocolHandler
	             → 文本帧转 String → JsonMessageDecoder → ... → business
	    business、会话表、线程模型完全一样, 只有 "消息怎么分界、连接怎么建立" 这一段不同。

	4. 两者能共用什么 (同时支持 TCP 客户端与网页客户端时)
	                                是否共用    对应本工程
	    Spring 生命周期、配置       共用        NettyServer (启动时绑两个端口)、NettyServerConfig
	    线程模型                    共用        同一组 bossGroup / workerGroup / bizGroup, 两个 ServerBootstrap 都用
	    连接参数                    共用        TCP_NODELAY、高低水位等 ChannelOption
	    空闲检测                    同一个类    IdleStateHandler (有状态, 仍然每个连接 new)
	    业务处理                    共用        ServerBusinessHandler (@Sharable 单例)
	    会话表                      共用        ChannelSessionManager: 存的是 Channel, 不关心是 TCP 还是 WebSocket
	    消息模型                    共用        Message、MessageEnum, LOGIN / CHAT / PING / KICKED 等语义
	    JSON 格式                   共用        {"content":"hi","to":"jerry","type":"CHAT"}
	    JSON ⇄ Message 转换         基本可以    JsonMessageDecoder / JsonMessageEncoder, 加适配 Handler 即可复用
	    HTTP 推送、日志格式         共用        NettyPushController、类名 方法名 invoke, userId=...
	    消息边界、握手              各写一份    TCP: LineBasedFrameDecoder + StringDecoder / StringEncoder
	                                            WS : HttpServerCodec + HttpObjectAggregator + WebSocketServerProtocolHandler
	    Pipeline 组装               各写一份    NettyServerInitializer + 新的 WebSocket Initializer
	    端口                        各占一个    9000 / 9001

	    并排看:
	        TCP 9000: Head → idle → LineBasedFrameDecoder → StringDecoder ─────────────────┐
	                                                                                        ├→ JsonMessageDecoder → [bizGroup] ServerBusinessHandler
	        WS  9001: Head → idle → HttpServerCodec → HttpObjectAggregator                  │        (共用)                    (共用)
	                       → WebSocketServerProtocolHandler → 帧转 String ──────────────────┘
	                         └──────────────── 只有这一段不同 ────────────────┘

	    复用 JSON 编解码器的小技巧:
	        · 入站: 加一个 MessageToMessageDecoder<TextWebSocketFrame>, 把 frame.text() 交给下一站, 后面原样接 JsonMessageDecoder;
	        · 出站: JsonMessageEncoder 输出 String, 再加一个 MessageToMessageEncoder<String> 包成 TextWebSocketFrame;
	        · 每个方向只多一个十来行的适配类, JSON 编解码器不用重写。

	5. 共用带来的效果: 跨协议互聊自动成立
	    tom 用终端客户端 (TCP), jerry 用网页 (WebSocket):
	        tom 发 CHAT → TCP Pipeline 解码 → ServerBusinessHandler → 会话表找到 jerry 的 Channel
	        → channel.writeAndFlush(Message) → jerry 的连接是 WebSocket Pipeline, 自动编码成 WebSocket 帧 → 浏览器收到
	    业务代码里没有一行判断 "对方是 TCP 还是 WebSocket":
	    同一个 Message 写到哪条连接上, 就由那条连接自己的 Pipeline 决定怎么编码。
	    这正是 Netty 把 "协议" 与 "业务" 拆开的价值 (② 处理链 与 ④ 编解码 分开的原因)。
	    客户端同理: Netty 客户端想走 WebSocket, 只需把 NettyClientInitializer 中的分界 Handler
	    换成 HttpClientCodec + WebSocketClientProtocolHandler, ClientHandler、重连、心跳、JSON 编解码都能共用。

	6. 怎么选
	    · 客户端是浏览器 → 只能用 WebSocket (服务端用 Netty 或 Spring WebSocket 实现均可);
	    · 客户端是原生程序 (桌面 App、Android、iOS、设备、其他服务) → 自定义 TCP 协议更直接、更省资源 (本方案路线);
	    · 两种都有 → Netty 开两个端口、两条 Pipeline, 共用业务 Handler 与会话表, 两边用户可以直接互聊。
	    · 以后要支持网页客户端, 代价约为: 1 个 WebSocket Initializer + 2 个适配 Handler + NettyServer 多绑一个端口。
